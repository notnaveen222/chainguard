Rubric 01Domain Knowledge & Problem Statement

Modern software is assembled, not written. A typical Node.js application declares 15–40 direct dependencies but installs 800–1,500 packages once transitive dependencies resolve; a Python application installs 200–400. Each is code that runs with the full privileges of the developer who installs it, and later of the production process that runs it.

Why the ecosystem is structurally attackable

  • Install-time execution. npm runs preinstall, install and postinstall hooks automatically; Python executes setup.py from a source distribution. Code runs before the developer invokes anything — on machines holding cloud credentials, SSH keys and signing tokens.
  • Transitive trust is unbounded. Installing one package trusts its entire closure and every maintainer in it.
  • Publication is effectively unauthenticated. No review; names are first-come-first-served.
  • Human name resolution is fuzzy. Nobody reliably distinguishes python-dateutil from python-dateutils.

Two problems, one pipeline

Problem A — malicious packages (detection). Signature scanning fails structurally: every malicious package is new by construction, and most are removed within days, so a signature arrives after the damage. Detection must generalise from behaviour, not identity.

Problem B — alert fatigue (prioritisation). SCA tools match versions against advisory databases and report every hit — 150–300 findings on a real project. Teams cannot triage that, so they triage nothing. The root cause is that the report is mostly irrelevant: a CVE in a dependency matters only if the application can actually reach the vulnerable function, and published measurements put that fraction well under 5%.

Problem statement. Given a project P with manifest M and source S, and dependency closure D(M):

(A) for each d ∈ D(M), decide whether d is malicious using only statically observable properties, generalising to unseen packages, and emitting auditable evidence.

(B) for each vulnerability v affecting some d, decide whether the vulnerable symbol is reachable from an entry point of S, and emit the call path as proof.

Subject to: no package is ever executed; and uncertainty in (B) always resolves to reachable, because a false “unreachable” conceals an exploitable flaw.

Scope boundaries, stated deliberately

Out of scope: dynamic/sandbox analysis (evadable by triggered payloads, needs isolation infrastructure); full JavaScript call-graph construction (dynamic require, bundlers and monkey-patching make it a research problem — attempting it would produce something that looks like reachability analysis and silently returns wrong answers); build-system provenance (SLSA), which proves origin, not safety.

Synthesis

  • Detection has converged on behaviour, not signatures. Every recent detector models what a package does.
  • Three families, one trade-off. Static ML is fast, cheap and measurable but bounded by feature quality; dynamic analysis sees real behaviour but needs sandboxing and is evaded by triggers; LLMs generalise well but are slow, costly and — the recurring criticism — hard to evaluate with stable precision and recall.
  • Evasion is escalating. 3.8× growth in evasion technique use between 2020 and 2024–25 [#7].
  • Prioritisation is acknowledged but under-served. Reachability was named a core SCA task in 2019 [#21]; in 2025 false positives and exploitability are still top SBOM barriers [#27]. Six years, same gap.

Positioning

ChainGuard sits deliberately in the static + classical ML family — measurable, offline, free to run — and adds the reachability layer the detection literature omits. The LLM is used only to explain verdicts, never to make them, precisely because the reviewed LLM literature identifies evaluation instability as its central weakness.

3.2  Detection methodology

Why AST parsing, not pattern matching

A regex for eval( matches the word in a comment, a docstring, or a variable named evaluate. An AST sees a genuine call node. More importantly it resolves aliases: import subprocess as sp then sp.run(...) is invisible to text search and explicit in the tree. Parsing is also what makes analysing hostile code safe — ast.parse() builds a tree without evaluating anything.

Core invariant

No package is ever executed. No pip install, no npm install, no setup.py invocation anywhere in the system. When a parse fails, the analyser degrades to text scanning and sets a flag, so the feature vector records reduced visibility rather than reporting a file clean that it never actually read.

Composite signals — the key design idea

Reading the environment is unremarkable. Making an HTTP request is unremarkable. Doing both in one file is the shape of credential theft, and no individual detector can observe that co-occurrence. Per-file analysers record behaviour flags; a second pass derives composites from them.

Validated empirically: across twelve popular real packages (express, axios, webpack, requests, flask, rich and others) not one composite signal fired, while both malicious samples triggered them immediately. Individual sinks are noisy; composition is precise.

Typosquat detection — four mechanisms, not one

Prior work [#10] notes Levenshtein-only detection has high error rates. The implementation combines keyboard-adjacency-weighted Damerau–Levenshtein (adjacent-key substitution and transposition cost 0.6, not 1.0, because swapping adjacent characters is the most common typing error), homoglyph substitution, structural variants (separators, affixes), and scope confusion — against 614 npm + 518 PyPI popular names generated and committed for reproducibility.

The most important methodological decision

Malicious samples come from an archive — those packages were removed years ago, so they have no live registry metadata. Benign samples are fetched live and have all of it. Feeding registry metadata to the classifier would let version_count > 0 separate the classes perfectly — not by detecting malware, but by detecting which corpus a sample came from. The model would report near-perfect metrics and be worthless, and the failure would be invisible: the numbers would simply look excellent.

Two countermeasures, enforced in code: metadata is reconstructed only from inside the archive (fields an attacker equally controls), and five registry-only features are zeroed for every training sample inside the matrix builder so no caller can bypass it.

The cost is that the model cannot learn “published yesterday” as evidence. That is the correct trade: a feature available for only one class in training is not a feature, it is the label.

Benign samples are real popular packages, not toy examples. The classifier must separate malware from real library code — full of network calls, subprocess use and minified bundles. A corpus of hand-written clean examples produces a model that scores beautifully and collapses on first contact with reality.

3.4  Reachability methodology

INPUT :  project source S, package p, vulnerable symbols V
OUTPUT:  verdict, call path

1  G ← build call graph over S
       nodes = module scopes ∪ function scopes
       edges = intra-app calls ∪ import edges
2  A ← import names actually provided by p        # pyyaml → yaml
3  if no module of S imports any name in A:
       return NOT_IMPORTED                        # strongest negative
4  if V = ∅:
       return ASSUMED_REACHABLE                   # fail-safe: cannot rule out
5  E ← entry points = modules imported by nothing else
6  # Pass 1 — module-level seeds only, so any path found is a real call chain
   path ← BFS(G, seeds = module scopes of E, target = calls into p.V)
   if path ≠ ∅: return REACHABLE, path
7  # Pass 2 — add public functions of entry modules (assumed externally callable)
   path ← BFS(G, seeds ∪ public functions of E, target = same)
   if path ≠ ∅: return REACHABLE, path
8  return SYMBOL_NOT_CALLED

Three decisions that make this work

  • Graded verdicts, not a boolean. NOT_IMPORTED (high confidence) is a far stronger claim than SYMBOL_NOT_CALLED (medium), and both differ from ASSUMED_REACHABLE (low). Collapsing these throws away the distinction that makes output actionable.
  • Two-pass search, because proof quality differs. Pass 1 starts only from module-level code, so any path it finds is a genuine call chain. On the demo this is the difference between a one-hop match and the full four-step trace.
  • Distribution names are not import names. pip install pyyaml gives import yaml; pillow gives PIL. Conflating them produces a confident false “safe” verdict — the worst possible output. Resolution is derived from each downloaded archive.
Fail-safe direction

Every uncertain case resolves to reachable. A false “reachable” costs an engineer ten minutes; a false “unreachable” hides an exploitable vulnerability. Related: a package that could not be downloaded has no signals and scores 0.0 — reporting that as clean would be a false all-clear in exactly the case where the tool is most useful, so such packages are reported separately as “Not inspected — NOT confirmed clean.”

3.5  Evaluation methodology (gap G3)

DecisionRationale
Grouped splitting by package nameDifferent versions of one package, and repeat uploads from one campaign, must never span the train/test boundary. Without grouping, a near-duplicate of a test sample sits in training and every score inflates. This single choice separates an honest number from a flattering one.
Out-of-fold reportingEvery figure comes from a model that had not seen that sample.

HonestyLimitations & Future Work

Stated plainly, because a security tool that overstates its certainty is worse than one that admits a gap.

  1. npm reachability is import-level only. Symbol-level JavaScript analysis requires solving dynamic require, bundler output and monkey-patching.
  2. “Not statically reachable” ≠ “not exploitable.” Dynamic dispatch, getattr indirection and reflection are not resolved.
  3. Survivorship bias. Training malware is malware that was caught; real recall is likely below the measured 0.939.
  4. Artificial class balance. The corpus is ~50/50; a real registry is closer to 1-in-10,000, so deployment precision would be lower.
  5. Structural features rank high partly because malicious samples are small droppers and popular benign packages are large libraries — a corpus property as well as real signal.
  6. The curated symbol table covers ~35 packages, so many advisories resolve to ASSUMED_REACHABLE rather than a precise verdict.
